# ccm Phase 2 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:subagent-driven-development. Steps use checkbox (`- [ ]`) syntax.

**Goal:** Make ccm the single, simple entry point: default launch args (synced to T3), a status line showing account + limits inside every Claude session, and a full-screen dashboard opened by bare `ccm`.

**Architecture:** Three independent packages (`internal/config`, `internal/statusline`, `internal/dash`) plus thin wiring in `internal/cli`. Launches keep going through `cli.runAccount` (which gains default args). The status line reads a short-lived usage cache so it stays fast.

**Tech Stack:** Go 1.27; new allowed deps: `github.com/charmbracelet/bubbletea`, `github.com/charmbracelet/lipgloss`, `github.com/charmbracelet/bubbles` (dashboard only).

**Spec:** `docs/superpowers/specs/2026-11-19-multiclaude-design.md` §"Phase 2 backlog" (binding), plus the phase-1 Global Constraints in `docs/superpowers/plans/2026-11-19-multiclaude.md`.

## Global Constraints (phase 2 additions)

- Config file: `<AccountsRoot>/config.json`, mode 0600, atomic write: `{"defaultArgs":[...],"accounts":{"<name>":{"args":[...]}}}`. Missing file means empty config.
- Arg order: `defaultArgs` → `accounts[name].args` → typed args. Applied ONLY to interactive launches (`ccm <name>`, `run`, `best`, dashboard). Never to internal `claude auth …` calls, plain `claude`, or the shim.
- T3: `ccm t3-sync` sets each claude instance's `config.launchArgs` (a single string, args shell-quoted and space-joined) to the merged defaults + account args. It replaces only the launchArgs that ccm wrote before; a user-edited value is preserved, with a warning. Track the last ccm-written value in `state.json` under `t3LaunchArgs` (C1: hold the mcp sync lock, or use a separate `t3.lock`).
- Writing `~/.claude/settings.json` is allowed ONLY for `ccm statusline install`, and only after showing the exact change, asking `[y/N]`, and backing up to `settings.json.ccm-backup-<unix>`. `ccm statusline uninstall` restores the previous `statusLine` value. This is a user-requested exception to the "never write ~/.claude" rule.
- Status line: `ccm statusline [--wrap "<cmd>"]` reads Claude's status JSON on stdin. If `--wrap` is given, it runs that command with the same stdin and prints its output first, then ` │ ccm: <account> 5h <x>% · 7d <y>%`. Must return in <150 ms: it reads `<AccountsRoot>/cache/usage.json` (written by `ccm status` and the dashboard), and when that is older than 60 s it spawns a detached `ccm status --refresh-cache` (with a lock so only one runs) and prints the cached values. Missing cache → `ccm: <account>`. The account comes from `CLAUDE_CONFIG_DIR` (unset → main).
- Main account email: when the registry email is empty, `list`, `status` and the dashboard show the email from `claude auth status` / the cache.
- Dashboard: bare `ccm` (no args) and `ccm dash`. Keys: ↑/↓ or j/k select, ⏎ launch (mode B: hand the terminal to claude via `tea.ExecProcess`, return to the dashboard on exit), `b` best, `n` new Terminal.app window (`osascript -e 'tell application "Terminal" to do script "<quoted ccm path> <name>"'`), `l` login, `a` add (prompts name + email), `d` doctor (shows the summary in a pane), `s` sync, `t` t3-sync, `r` refresh, `?` help, `q`/Ctrl-C quit. Auto-refresh every 30 s. Shows a `⚠ skip-permissions` badge when the merged args contain `--dangerously-skip-permissions`. TODAY tokens are shown as `in/out` and `cache` separately.
- All tests use t.TempDir and fakes. Never touch the real HOME, Keychain, network, pbcopy or osascript in tests.

## Review Focus

1. Status line latency when the cache is stale or missing, and when the Keychain is locked → still <150 ms, never blocks or prompts.
2. `t3-sync` launchArgs: a user-edited launchArgs is never clobbered.
3. Dashboard launch returns cleanly to the dashboard after claude exits or crashes, with the terminal state restored.
4. `statusline install` on a settings.json that has no `statusLine`, a non-command `statusLine`, or an already-wrapped one (idempotent).
5. Args with spaces or quotes round-trip through config → argv → T3 launchArgs string.

### Task P1: config + default args + T3 launchArgs + main email
Files: `internal/config/*`, `internal/cli/{run.go (merge args), config_cmd.go, list.go, status.go}`, `internal/t3/*` (launchArgs), `internal/status` (email fallback field), dispatch entry for `config`.
Commands: `ccm config show`, `ccm config set default-args <args...>`, `ccm config set args <account> <args...>`, `ccm config clear default-args|args <account>`.
Tests: merge order; run passes merged args (fake runner argv); internal auth calls never get them; t3 launchArgs quoting and round-trip; user-edited launchArgs preserved; main email fallback in list/status.

### Task P2: status line
Files: `internal/statusline/*`, `internal/cli/statusline_cmd.go`, cache writer in `internal/status` (`WriteCache`/`ReadCache`), `ccm status --refresh-cache`.
Tests: render with and without `--wrap` (fake command); cache fresh / stale (spawns refresher via an injected func) / missing; account from env; install/uninstall diff, idempotence, backup, confirm prompt; latency test with a slow fake Keychain must not be called on the hot path.

### Task P3: dashboard
Files: `internal/dash/*` (model, view, keys, commands), `internal/cli/dash_cmd.go`, bare-`ccm` dispatch.
Depends only on existing APIs: `status.Collect`, `cli` launch helper (expose `(*App) LaunchAccount(ctx, name string, extra []string) int` if needed — P1 owns run.go; P3 calls it), registry, doctor.Summary.
Tests: model update tests per key (teatest or direct Update calls), view snapshot for 2 accounts, ⏎ produces an ExecProcess cmd with the right env and args, `n` produces the osascript argv via an injected runner, refresh tick.

### Task P4: docs + live checklist
README sections for config, statusline and dash; `docs/e2e-checklist.md` phase-2 items.
